INCIDB Technical Documentation

The seven tables, the sources they come from, the coverage each enrichment column actually has, and how to query the result.

1. What is in the snapshot

Seven tables, exported as pipe-delimited UTF-8 CSV and Apache Parquet with identical columns:

  • 18,583 products — one row per Open Beauty Facts product carrying a usable on-pack ingredient declaration, with the raw declaration kept verbatim so the parse can be re-derived.
  • 5,925 brands — brand identities as recorded upstream.
  • 46,009 distinct canonical INCI names — the result of canonicalising every raw label token, enriched from CosIng where CosIng lists them.
  • 341,904 ordered composition links — preserving label order in position_index.
  • 77,059 name-map rows — how each raw label token was resolved, and by which method.
  • 269 fragrance_allergens rows — the EU Annex III fragrance-allergen entries, one row per legal name and INCIDB match, review rows and unmatched names included.
  • 631 regulatory_status rows — EU Annex II–VI status per ingredient and list entry, conditions verbatim. A row exists only where a list says something.

2. Sources and the join

Three sources, each with a documented join. Every source file's URL, download timestamp and SHA-256 is recorded in the build_report.json shipped with the data.

  • Open Beauty Facts — the product corpus (barcodes, brands, the source's own categories_tags, raw ingredient declarations) under the Open Database License (ODbL).
  • European Commission CosIng — the ingredient inventory: functional categories, CAS and EC numbers, chemical descriptions, restrictions, and Annex II–VI membership. Joined on exact canonical name; unmatched names are NULL in every CosIng-derived column, never a placeholder. The Annex II–VI exports also feed regulatory_status, matched by the CosIng glossary name or the CosIng "Identified INGREDIENTS" name only (no CAS route). Absence of a row is not a status, and nothing in it is legal advice.
  • EU fragrance allergens. The 81 labelling entries of Annex III to Regulation (EC) 1223/2009, as amended by Regulation (EU) 2023/1545 (consolidated text of 18.05.2026), are matched to INCIDB by exact INCI name, then by the collective label name the Regulation prescribes (e.g. "Rose Ketones"), then by CAS number for chemically defined substances only. Botanical CAS hits are shipped as review rows, never flags. 121 names are flagged; 46.9% of products contain at least one. About 2.7% of products list ingredients as unsplit text that the allergen flags do not reach. The US FDA has not yet published its MoCRA fragrance-allergen list, so this dataset carries no US flag.
  • Authored layer — 144 comedogenic ratings transcribed from one published table, and 272 rule-derived fungal-acne flags. Both carry their citation per row in rating_source, and are NULL everywhere else.

3. Measured coverage

Reported two ways, because the two differ by an order of magnitude and quoting only one would mislead:

  • CosIng match (any): 11.6% of the 46,009 distinct canonical names; 83.9% of the 341,904 ingredient occurrences across product labels.
  • functions: 11.5% of distinct names; 82.9% of label occurrences.
  • cas_number: 8.7% of distinct names; 77.6% of label occurrences.
  • chemical_description: 9.0% of distinct names, 4,099 distinct values.

A label corpus contains far more distinct strings — botanical variants, multilingual spellings, marketing tokens — than any regulatory inventory lists, which is why the first number in each pair is low. The slots on a real label are filled overwhelmingly by ingredients CosIng does cover, which is why the second is high. Neither number alone describes the data.

4. Canonicalisation

Raw label tokens are resolved to canonical INCI names by an explicit ordered procedure — entity decode, character strip, whitespace collapse, upper-case, then exact match, cleaned match, a small cited typo map, percentage stripping, parenthesis stripping, a synonym map, slash-variant splitting, and concatenation splitting only where both halves match the inventory. Tokens that none of them resolves are re-split by explicit rules (brackets, (and), bullets, colons, . separators, line breaks), never fuzzily: every recovered name must match the inventory or the cited maps exactly, and unmatched text between recovered names is kept as unresolved_residual. A token that nothing resolves is kept verbatim and recorded as unresolved, never guessed. The method used is stored per row in ingredient_name_map.method, with part_index and split_rule recording each cut, so every decision is auditable and reversible.

5. Quick start — PyArrow & Pandas

import pyarrow.parquet as pq

ingredients = pq.read_table('ingredients.parquet').to_pandas()
links = pq.read_table('product_ingredients.parquet').to_pandas()

# Coverage the way it actually matters: weighted by label occurrence.
merged = links.merge(ingredients, on='ingredient_id', how='left')
print(merged['functions'].notna().mean())

# EU Annex III fragrance allergens
allergens = ingredients[ingredients['is_common_allergen'] == 1]

6. Quick start — DuckDB

import duckdb

duckdb.query("""
SELECT f.function, COUNT(*) AS label_slots
FROM 'product_ingredients.parquet' pi
JOIN 'ingredients.parquet' i USING (ingredient_id)
CROSS JOIN UNNEST(string_split(i.functions, ';')) AS f(function)
WHERE i.functions IS NOT NULL
GROUP BY 1 ORDER BY 2 DESC LIMIT 10;
""").show()

# Audit the canonicalisation itself
duckdb.query("""
SELECT method, COUNT(*) AS n
FROM 'ingredient_name_map.parquet'
GROUP BY 1 ORDER BY 2 DESC;
""").show()
